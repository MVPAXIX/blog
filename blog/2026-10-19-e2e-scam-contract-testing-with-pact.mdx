# The E2E Scam: Why Contract Testing with Pact Wins

The most costly lie in the modern software architecture is end-to-end (E2E).

It has been a standard practice of the industry to start a heavy headless browser to simply ensure that a backend API returns 200 OK for years. Brittle Cypress/Selenium suites for microservice validation makes the entire delivery pipeline choke when Distributed Engineering Teams are used.

In the case of Offshore Software Development, this makes it impossible to scale up. In case the frontend developer modifies the name of a CSS class the E2E test breaks and the backend deployment cannot be executed. Without proper Remote Team Management, test logs turn into false positives and go against your Remote Work Culture.

A test performed on a microservice via a browser, is not integration testing. It's an anti-pattern for architecture.

## The Sense of Security of E2E Safety

E2E suites are a drag on engineering velocity, when they're long running. When a CI pipeline runs for 45 minutes, developers have no option but to have to context switch, thereby disrupting Asynchronous Work Strategies.

If the developers are waiting for a fragile test suite, they're not shipping features. This friction generates a tremendous amount of frustration, reducing Remote Talent Retention, with the best engineers becoming burn out firefighters on DevOps. In addition, large E2E suites are hard to be run locally. It greatly slows down Remote Developer Onboarding: new developers have to spend the first week to get this huge test setup to compile on their laptop.

## The Paradigm Shift: Consumer-Driven Contracts

Now comes in Pact and Consumer-Driven Contract Testing. You don't have to spin up the whole world to test an integration, instead you test the mathematical contract between the consumer (frontend) and the provider (backend) in complete isolation.

The paradigm shift is thus as follows:

- **The Rules are written by the Consumer:** The frontend specifies a lightweight test that specifies precisely what JSON payload it expects to be provided with. This creates a "Contract."
- **The Provider Verifies:** The backend performs a sub-second unit test on that same Contract to make sure that the API response to it is exactly what they are expecting.

No seed databases are provided. No browsers are started. Rapid and isolated validation in milliseconds.

## This is also known as Pipeline Reality for Global Engineering

Distributed Agile Teams have a super power: Contract Testing.

The backend engineer in Africa can check at any time whether their API meets the Contract without the need to join into a synchronous zoom call, when a frontend engineer in Europe updates it. This "integration day" nightmare is eliminated by a frictionless Cross-Cultural Team Integration.

Contracts are essentially “living” and can be executed as documentation. Once an API has changed, then the contract will fail right away in CI before the code is even merged, ensuring that independent teams can deploy at their own pace without breaking downstream APIs.
